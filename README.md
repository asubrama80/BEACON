# BEACON

BEACON is an emergency communication and incident war-room platform. It lets responders send emergency alerts to contacts and groups, manage incidents, and collaborate in real time — chat, audio/video, and screen sharing — inside incident-scoped War Rooms that also support temporary, incident-specific guest access.

## Architecture

- **Modular monolith** — a single deployable frontend and backend, organized into feature modules built incrementally.
- **REST API** between frontend and backend, with **WebSocket** for realtime incident chat and collaboration.
- **Provider abstraction** for SMS, email, and realtime collaboration, so providers can be swapped without touching application logic.
- Portable and deployable under any domain, cloud, or hosting provider — no runtime dependency on corporate VPN, Active Directory, Microsoft 365, HR systems, or MDM.
- **Contacts** (alert recipients) and **application users** (people who log in) are separate concepts. Registered responders access Incident War Rooms as authenticated users; guests get incident-scoped temporary access.
- The stakeholder prototype at [docs/reference/beaconstakeholderprototype.html](docs/reference/beaconstakeholderprototype.html) is the approved **UI/UX source of truth**.

## Technology stack

| Layer | Technology |
| --- | --- |
| Frontend | React + TypeScript + Vite |
| Backend | Node.js + TypeScript + Fastify |
| Database | PostgreSQL + Drizzle ORM |
| Realtime | WebSocket |
| Deployment | Docker / Docker Compose + Nginx |

Permission-gated (`alerts.read/create/update/ready/cancel/recipients.read`, with recipient destination PII behind its own permission), server-side max-recipient safety limit, and an Alerts screen with an explicit Ready confirmation step. See [claude/prompts/09-alert-engine.md](claude/prompts/09-alert-engine.md) for the full design. This module does not send anything — no provider integration, retry logic, or delivery tracking exist yet.
- **Module 10 — Notification Providers: complete.** A provider-agnostic dispatch layer that submits Module 09's immutable READY Alert Recipient snapshots to an external SMS/Email provider — never re-resolving Contacts/Groups or re-rendering Templates. Mock (default, zero network calls), Twilio (SMS, via REST), and Amazon SES (Email, via the official SDK) adapters behind a central registry, selected by `SMS_PROVIDER`/`EMAIL_PROVIDER` env config; an unconfigured real provider fails safely at startup rather than silently falling back to mock. An explicit, separately-permissioned `alerts.dispatch` action (distinct from READY) with DB-enforced idempotency (a recipient can never be submitted twice), bounded retry with transient/permanent error classification, bounded concurrency, and an append-only `notification_dispatch_attempts` history free of PII/credentials. Provider acceptance is always called "submitted," never "delivered" — that distinction belongs to Module 11. See [claude/prompts/10-notification-providers.md](claude/prompts/10-notification-providers.md) for the full design. Delivery tracking, provider callbacks/webhooks, and the Incident Command Center are not implemented yet.
- **Module 11 — Delivery Tracking: complete.** Post-submission delivery tracking for Module 10's dispatched Alert Recipients — provider-neutral delivery states (`pending` → `delivered`/`undelivered`/`bounced`/`failed`), correlated purely by `(provider, providerMessageId)`, never by destination. A Twilio status-callback webhook with hand-rolled request-signature verification, and an SES-via-SNS event webhook with RSA-signature-verified message authenticity (SNS `SubscribeURL` is never auto-fetched — SSRF-safe by construction); both isolated from session auth/CSRF, idempotent via a DB-unique dedupe key, and immune to out-of-order/duplicate callbacks via a monotonic terminal-state rank rule. A development-only mock-delivery simulation endpoint (404 outside development/test) exercises the identical `processDeliveryEvent()` path real webhooks use. A safe aggregate delivery summary (never destination PII) is exposed on every Alert; a dual-permission-gated (`alerts.recipients.read` + new `alerts.delivery.read`) endpoint exposes per-recipient event history. Delivery callbacks continue to be processed for a CLOSED Incident or an already-dispatched Alert — historical reality is never erased. A single `ALERT_DELIVERY_COMPLETED` Incident-timeline/audit event fires exactly once, race-safe under concurrent completion. See [claude/prompts/11-delivery-tracking.md](claude/prompts/11-delivery-tracking.md) for the full design. Real Twilio/SES credentials were not available in this environment — Twilio/SES correctness was verified with synthetic signatures, not a live provider account. The Incident Command Center is not implemented yet.
- **Module 12 — Incident Command Center: complete.** A read-only, aggregating operational view over Modules 08-11's already-authoritative data — never a second incident/alert/delivery status model. One new endpoint, `GET /incidents/:id/command-center`, assembles a safe aggregate projection entirely from existing query/service functions: participant and commander summary (Module 08), Alert-status and delivery-outcome rollups across every Alert on the Incident (Modules 09-11), a bounded list of recent Alerts each carrying its own already-computed delivery summary, and a bounded recent-timeline slice. Gated by a new, deliberately global `incidents.command_center.read` permission (ADMIN/INCIDENT_COMMANDER/COMMUNICATION_MANAGER/AUDITOR/RESPONDER all granted — no row-level "assigned incident" concept exists in this codebase yet). A new "Command Center" tab on the Incident detail view surfaces this, plus a one-shot cross-page navigation hook that can open a specific Alert's detail modal or pre-select this Incident when quick-creating a new Alert — reusing the existing Alert flows rather than duplicating them. Remains fully readable on a CLOSED Incident; introduces no new mutation of its own. See [claude/prompts/12-incident-command-center.md](claude/prompts/12-incident-command-center.md) for the full design. Realtime chat, War Room, video, screen sharing, and guest access are not implemented yet.
- **Module 13 — Realtime Incident Chat: complete.** Persistent, incident-scoped realtime text chat for registered Users, built on WebSocket (`@fastify/websocket`) + Fastify + PostgreSQL — the database is always the source of truth, never the socket. Reuses Module 01's `chat_messages` table (adding only a `seq` tiebreaker column for deterministic ordering) rather than a second chat model. Every message is persisted before it is ever broadcast; a WebSocket connection reuses the exact same session-cookie authentication and `requirePermission()` authorization every REST route already uses (new `incidents.chat.read`/`incidents.chat.send` codes — AUDITOR gets read-only), plus Origin-header validation (the WebSocket-appropriate analogue of CSRF protection, since normal CORS doesn't cover the handshake). Chat history stays fully readable on a CLOSED Incident; new sends are rejected server-side. Plain text only, rendered by React as text — never `dangerouslySetInnerHTML` — so an XSS-shaped message body is always inert. The frontend reconnects with backoff and always re-fetches history from the durable REST endpoint on reconnect rather than trusting the socket to replay anything. See [claude/prompts/13-realtime-incident-chat.md](claude/prompts/13-realtime-incident-chat.md) for the full design, including two real bugs (a broadcast double-delivery and a sender-echo gap) caught and fixed during this module's own testing. War Room, audio/video, screen sharing, and guest access are not implemented yet.
- **Module 14 — War Room Foundation: complete.** The War Room domain model, lifecycle, access authorization, join/leave session tracking, and UI shell — deliberately provider-neutral. No RTC SDK (Agora/LiveKit/Twilio Video/WebRTC), no camera/microphone access, no meeting URL or media token anywhere. `NOT_STARTED → OPEN → ENDED`, where `NOT_STARTED` is the absence of a row rather than a stored value. A War Room *session* (`war_room_sessions`) is a genuinely separate concept from Incident *participation* (Module 08's roster) — joining never adds someone to the roster, and roster membership never implies having joined. New `incidents.war_room.read`/`manage`/`join` permissions (manage is Incident-Commander-level, mirroring `incidents.lifecycle.manage`'s existing exclusion for COMMUNICATION_MANAGER). Join/leave are database-level idempotent via partial unique indexes, not just service-layer checks. Closing an Incident does not auto-end its open War Room (a deliberate, documented limitation — the alternative would have required modifying Module 08's already-complete lifecycle code); new joins are independently blocked once the Incident is CLOSED, and an authorized manager can still End a stray open room afterward as a cleanup path. A prejoin confirmation step precedes every join; the media area is a fixed "Audio/video becomes available in Module 15" placeholder. See [claude/prompts/14-war-room-foundation.md](claude/prompts/14-war-room-foundation.md) for the full design. Audio/video, screen sharing, and guest access are not implemented yet — Module 15 requires a deliberate, separate operator-reviewed decision before any RTC provider work begins.
- **Module 17 — Guest Invitations: complete.** (Modules 15/16 — Audio/Video and Screen Sharing — remain deliberately deferred; this module and the two that follow do not require them.) Guest invitation creation, secure token issuance, notification delivery (reusing Module 10's provider abstraction directly, never the Alert Engine), lifecycle, expiry, revocation, and a public pre-verification landing page. A Guest never becomes a `users` row and never receives an RBAC role or permission at any point. Reuses the existing `guest_invitations` table (Module 01/08) as the sole identity anchor — Module 08 had already established this pattern via `incident_participants.guest_invitation_id`, so no separate `incident_guests` identity table was introduced. Tokens follow the exact `randomBytes`+SHA-256 pattern already established for session tokens; only the hash is ever persisted, and the raw token is exposed exactly once, in the creation response. Two partial unique indexes give race-safe duplicate-invitation detection (at most one active invitation per destination per Incident), not just a service-layer pre-check. New `incidents.guests.read`/`invite`/`revoke` permissions. A "Guest Invitations" tab on the Incident detail view (create/list/revoke, with the raw link shown once in a clearly-labeled DEV-ONLY banner), and a standalone public landing page at `/guest/invite/:token`, reached via a pathname check in `App.tsx` that renders entirely outside the authenticated app shell (this codebase has no routing library). See [claude/prompts/17-guest-invitations.md](claude/prompts/17-guest-invitations.md) for the full design. OTP verification (Module 18) and Guest roster/Chat/War Room integration (Module 19) are not implemented yet.
- **Module 18 — OTP Verification: complete.** Two-factor possession-and-control verification for a Guest invitation. A dedicated `guest_otp_challenges` table (attempt count, salted hash, issued/expires/consumed timestamps) rather than the single `otp_hash` column Module 01 provisioned, which couldn't track attempts or resend history. Codes are 6-digit, `crypto.randomInt`-generated (never `Math.random()`, never the prototype's static demo value), salted-SHA-256-hashed, server-enforced TTL, attempt-limited to lockout (even the correct code fails once locked), and resend supersedes the prior code under a partial-unique-index race guarantee. A brand-new `guest_sessions` table and matching `authenticateGuest()` middleware are entirely separate from registered-User sessions — separate cookie, separate CSRF pair, no `user_id` column anywhere, and re-validated (session, invitation, Incident state) on every request rather than trusting cookie expiry alone. Neither OTP request nor verify reject an already-verified invitation, so a Guest whose session later expires can always request a fresh code and get back in; the one-time `GUEST_VERIFIED` timeline event and idempotent `verified_at` transition still guarantee the state change itself happens exactly once, including under two genuinely concurrent correct submissions. A test-only OTP capture seam (mirroring Module 11's `sesFetchCert` pattern) exists purely in-process for the test suite — never a DEV API endpoint that could leak a code. The public landing page (Module 17) now owns the full request → verify → authenticated-confirmation flow. See [claude/prompts/18-otp-verification.md](claude/prompts/18-otp-verification.md) for the full design. Guest roster/Chat/War Room integration (Module 19) is not implemented yet.
- **Module 19 — Participant Management: complete.** Closes the loop Modules 17-18 opened: a verified Guest now actually participates in an Incident. Auto-enrolls a just-verified Guest into `incident_participants` (Module 08's roster) inside the same transaction as OTP verification, gated on first-time-only so a later re-authentication never resurrects a participant a manager has removed; race-safety comes from a new partial unique index, mirroring the existing User/Contact pattern exactly. Manager removal of a Guest eagerly revokes every active Guest session in the same transaction, making access denial immediate rather than waiting on cookie expiry. Extends Module 13 Chat (already schema-ready for Guest authorship via `participant_id`, never a `users` row) and closes a real gap in Module 14 War Room (which previously allowed a `'guest'` session row with no identity column requirement at all) with a new `guest_invitation_id` column, tightened check constraint, and matching partial unique index. New `requireGuestCapability()`/`requireGuestIncidentMatch()` guards gate Guest-facing Chat/War Room routes on the invitation's own granted capabilities and Incident scope — never RBAC, and never a client-supplied Incident id trusted without matching the Guest's own session. The Incident roster UI shows Guests with a badge, capability chips, and verification status; the public Guest portal now renders real Chat/War Room panels (reusing the same `useChatSocket` hook as the registered-User Chat) instead of a placeholder. No new RBAC permission codes were needed. See [claude/prompts/19-participant-management.md](claude/prompts/19-participant-management.md) for the full design, including the full Guest-isolation security matrix. This concludes the Modules 17→18→19 sequence — Modules 15/16 (Audio/Video, Screen Sharing) remain deliberately deferred, and Module 20 has not been started.
- **Module 20 — Audit: complete.** A trustworthy, searchable, authorization-controlled Audit search API and frontend, extending the existing `audit_logs` foundation (Module 01) rather than a parallel system — and deliberately distinct from the Incident timeline, which remains a separate, per-Incident operational record. Closed a real actor-model gap discovered during this module's coverage review: every Guest-initiated event (OTP request, verification success/lockout, session logout) was being silently misattributed to a fake `"system"` actor, since the write helper only ever inferred `user`/`system` and had no way to select the already-schema-supported `"guest"` actor type. Fixed by making the actor type explicit at the four genuinely Guest-initiated call sites, attributed to the same `guest_invitations` identity anchor Module 17 established — a real correctness fix, not new instrumentation. New keyset (cursor) pagination — deliberately different from every other list endpoint's page/pageSize convention, since Audit is a potentially very large, always-newest-first, append-only table where an ever-growing `OFFSET` doesn't scale. New global `audit.read` permission, granted only to ADMIN and AUDITOR (whose entire role description is compliance/audit review). No new audit event coverage was needed — a full review of all ~30 existing event types across Modules 02-19 found the write-side coverage already comprehensive. See [claude/prompts/20-audit.md](claude/prompts/20-audit.md) for the full design.
- **Module 21 — Dashboard & History: complete.** A real operational Dashboard, replacing the "Signed in" placeholder that stood in for it since Module 00 — assembled entirely from Modules 04/06/08/09/10/11's own authoritative data (Incident/Alert status counts, a global delivery summary, active Contact/Group counts, bounded recent-Incident/recent-Alert lists), mirroring the exact "never a parallel status model" discipline Module 12's Command Center already established, just applied platform-wide instead of per-Incident. A deterministic, always-explainable "Attention Required" section (alerts ready but not dispatched; delivery failures) reuses counts the Dashboard was already computing rather than inventing a severity score. Incident/Alert History were deliberately *not* built as new pages — the existing Incidents/Alerts pages already supported search, status (including CLOSED), and pagination since Modules 08/09; the one genuine gap, a date-range filter, was added directly to both existing list endpoints and pages instead of standing up a second history system. No new permission code was introduced — `GET /dashboard` reuses `incidents.read`, already held by every current system role. See [claude/prompts/21-dashboard-history.md](claude/prompts/21-dashboard-history.md) for the full design. This concludes the Modules 20→21 sequence — Modules 15/16 remain deferred.
- **Module 22 — Administration: complete.** Application Administration, built almost entirely by composing existing modules rather than duplicating them — User administration (Module 03) and Audit (Module 20) are linked to, never re-implemented. Two new permissions, `admin.read`/`admin.manage` (ADMIN gets both; AUDITOR gets read-only), gate four new endpoints: a sanitized `GET /admin/status` (application/database/security/provider-name/collaboration-status — an explicit allowlisted DTO, never a `process.env` dump or a credential, matching Module 27's still-untouched provider-configuration boundary), a read-only `GET /admin/roles` joining the existing seed-managed `roles`/`role_permissions`/`permissions` tables for role-to-permission visibility and per-role User counts (the existing `GET /roles`/`GET /permissions` endpoints never assembled together), and two genuinely new admin-privileged security actions distinct from Module 03's own `disableUser` (which already revokes sessions as a side effect): standalone session revocation (forcing re-authentication without deactivating the account) and admin-privileged MFA reset (deletes the credential/recovery codes, never reads the TOTP secret, forces re-enrollment) — both reuse the existing last-admin/break-glass safeguards and emit their own new audit event types (`USER_SESSIONS_ADMIN_REVOKED`, `MFA_ADMIN_RESET`) exactly once per action. A new Administration screen surfaces all of this, plus session-revoke/MFA-reset action buttons (with the same confirm-before-danger pattern as Module 03's existing "Disable user") added directly into the existing User detail modal. See [claude/prompts/22-administration.md](claude/prompts/22-administration.md) for the full design. Provider credential administration remains Module 27's boundary and was deliberately not touched.
- **Module 23 — Security Hardening: complete.** A systematic security review and hardening pass across Modules 00-22, not merely headers and a handful of tests — full findings/threat-model/dependency-review documented in [docs/security/SECURITY_REVIEW.md](docs/security/SECURITY_REVIEW.md). Two real vulnerabilities were found and fixed: a notification-provider config bug where an unrecognized `SMS_PROVIDER`/`EMAIL_PROVIDER` value (e.g. a typo) silently fell back to the mock provider instead of failing startup, and a Guest-chat gap where a removed Guest's already-open WebSocket could keep sending messages (session revocation blocked *future* handshakes but never re-validated an existing connection) — both fixed, the latter by re-checking the participant's live status on every send rather than trusting a connection-time snapshot. A genuine TOCTOU race in the last-active-administrator safeguard was also found and closed: the check-then-act sequence was unlocked and non-transactional, so two concurrent disable requests against two different admins could both pass before either committed; `disableUser()`/`removeRole()` now run inside a transaction with `SELECT ... FOR UPDATE` row locking, proven closed with a genuine concurrency test. Added `@fastify/helmet` (zero HTTP security headers existed beforehand), a production `CORS_ORIGIN` fail-fast check, and a blanket `Cache-Control: no-store` (this API serves no cacheable content). A full audit — CSRF coverage across all 63 state-changing routes, CORS/WebSocket-Origin strictness, SQL injection, XSS, logging hygiene, frontend storage, secret scanning, RBAC/IDOR coverage, and a dependency review — found the existing baseline from Modules 00-22 already strong; those findings are documented, not re-tested here. See [claude/prompts/23-security-hardening.md](claude/prompts/23-security-hardening.md) for the full implementation log. This concludes the Modules 22→23 sequence — Modules 15/16 remain deferred, and Module 27 (Provider Configuration & Administration UI) remains untouched; provider configuration stays environment-driven.

Found and fixed a real WebSocket bug: rapid unwaited chat sends on the same connection could be persisted and broadcast out of order, since each frame was handled by an independent, unserialized async task — fixed with a per-connection FIFO processing chain. ## Prerequisites

- Node.js 20+ and npm 10+
- Docker and Docker Compose (for the PostgreSQL development service; optional if you run PostgreSQL yourself)

## Local development setup

```bash
cp .env.example .env
npm install
```

### Start PostgreSQL (Docker)

```bash
docker compose up postgres
```

### Start the backend

```bash
npm run dev --workspace backend
```

Backend listens on `http://localhost:4000` by default (`BACKEND_PORT` in `.env`). Verify with:

```bash
curl http://localhost:4000/health
```

### Start the frontend

```bash
npm run dev --workspace frontend
```

Frontend serves on `http://localhost:5173` by default (`FRONTEND_PORT` in `.env`).

### Set up the database

With PostgreSQL running (Docker or otherwise) and `DATABASE_URL` configured in `.env`:

```bash
npm run db:migrate   # apply committed migrations
npm run db:seed      # idempotently ensure the 5 system roles + Module 03/04/05/06/07 permissions exist
npm run db:status     # list applied migrations, seeded roles, and permissions
```

`GET /health` reports database connectivity alongside application status (`{"database": {"connected": true|false}}`) without exposing credentials. See [database/README.md](database/README.md) for schema layout, migration policy, and backup/restore steps.

### Create a local user

```bash
npm run bootstrap-user --workspace backend
```

Interactive prompt (never accepts a password via flag/env var). Answer "y" to the break-glass question only for the single local emergency admin account — see [claude/prompts/02-authentication.md](claude/prompts/02-authentication.md) for the full break-glass process, including enrolling MFA immediately afterward. You can also assign a role (e.g. `ADMIN`) at creation time — this is the only way to grant the very first administrator, since assigning roles through the API itself requires already being one.

### Start everything with Docker Compose

```bash
docker compose up
```

### Start everything without Docker

```bash
npm run dev
```

Run from the repository root (applies to the `frontend`, `backend`, and `database` workspaces):

