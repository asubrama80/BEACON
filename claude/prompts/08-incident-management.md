# Module 08 — Incident Management

## Scope

A durable operational record for a BEACON emergency incident: identity, severity, an explicit
lifecycle state machine, an Incident Commander (a registered User, never a Contact), a
Participant roster (registered Users and Contacts, never Guests), and an append-only operational
Timeline distinct from the global audit log. This module is the container the rest of the
platform will attach to — it does **not** send alerts, run a War Room, provide chat, or invite
guests. Those are explicitly out of scope and are the job of later modules (09 Alert Engine, 12
Incident Command Center, 13 Realtime Chat, 14+ War Room, 17 Guest Invitations, 18 OTP
Verification).

## Architecture / boundaries

- **Incident Commander vs the `INCIDENT_COMMANDER` RBAC role are distinct concepts.** The RBAC
  role grants permissions (via `requirePermission`); the Commander is a per-Incident assignment
  stored on `incidents.commander_id`. Any active User can be assigned Commander on a given
  Incident regardless of their global role, and assigning/changing a Commander never writes to
  `user_roles`. Verified live: assigning a User with zero role assignments as Commander leaves
  `user_roles` empty for that User both before and after.
- **Participants are User or Contact, never Guest.** `incident_participants.participant_type`
  remains schema-compatible with a future `'guest'` value, but no Guest creation, invitation, or
  OTP verification path exists in this module — enforced by never emitting the value.
- A Contact added to an Incident roster gains **no BEACON login access** — the frontend surfaces
  this explicitly ("This adds the Contact to the Incident roster only. It does not grant BEACON
  login access or send an invitation.").
- The Incident Timeline (`incident_timeline_events`) is a separate, incident-scoped, append-only,
  PII-free operational log — distinct from the global `audit_logs` table used for compliance/
  security audit. Every mutating operation writes to both, in the same transaction.

## Data model / migration

New migration `0008_conscious_legion.sql` (generated by drizzle-kit, applied to `beacon_dev`):

- `incidents` gains `incident_number` (unique), `created_by` (FK → `users`, `set null`),
  `closed_at`; a new index on `severity`.
- New `incident_number_seq` Postgres `SEQUENCE` (global, never reset).
- New `incident_timeline_events` table: `id`, `seq` (serial, globally ordered), `incident_id` (FK
  cascade), `event_type`, `actor_user_id` (FK set null), `metadata` (jsonb, no PII), `occurred_at`.
- Two new partial unique indexes on `incident_participants` — one on `(incident_id, user_id)`,
  one on `(incident_id, contact_id)` — each scoped `WHERE status != 'removed'`, the real
  database-level guarantee against duplicate active participants.

The existing `severity` (`info|warning|high|critical`) and `status`
(`open|active|resolved|closed`) check constraints from Module 01 were preserved unchanged — they
already matched the terminology this module needed.

## Identifier strategy

`INC-{year}-{6-digit nextval}` via `generateIncidentNumber()`, backed by a single global
`nextval('incident_number_seq')` — atomic and lock-free under concurrent creation. The sequence
is deliberately **not** reset per calendar year (avoiding year-rollover-safe per-year counter
complexity); the year in the formatted string is simply the current year at creation time. This
was a conscious tradeoff, not an oversight — flagged as a known limitation below.

## Severity model

Reused the existing schema values unchanged: `info`, `warning`, `high`, `critical`.

## Lifecycle / state machine

`OPEN → ACTIVE → RESOLVED → CLOSED`, plus `RESOLVED → ACTIVE` (reopen). `CLOSED` is strictly
terminal — there is no reopen-from-closed path. Every transition is a single conditional
`UPDATE incidents SET status = ? WHERE id = ? AND status = <expected-prior-status>`; zero rows
affected is disambiguated into 404 (no such Incident) vs 409 `invalid_transition` (wrong state)
via a follow-up `SELECT`. This update-with-affected-row-count-check **is** the concurrency guard,
not a courtesy check layered on top of one.

## CLOSED semantics

Once `CLOSED`, an Incident's metadata, roster, and commander can never change, and no further
lifecycle transition is possible. Enforced server-side (not just in the UI) via `SELECT ... FOR
UPDATE` row-locking inside each mutating transaction for operations that aren't themselves a
direct conditional `UPDATE` (commander assignment, participant add). Live-verified: after `close`,
metadata `PATCH`, participant add, commander change, and `activate` all return `409` with
`incident_closed` / `invalid_transition`.

## Commander model

`incidents.commander_id` references `users.id` (`set null` on delete), nullable. Assignment
requires the target to be an active, registered `User` (reuses `findSafeUserById`). Assigning or
re-assigning is a transaction: row-lock the Incident, verify not closed, update `commander_id`,
append a `COMMANDER_ASSIGNED` or `COMMANDER_CHANGED` timeline+audit event (re-assigning the same
Commander is a silent no-op). **No RBAC role, permission, or `user_roles` row is ever touched.**

## Commander vs RBAC verification

Live-verified directly against `user_roles`: a User with zero role assignments was assigned as
Commander, and `user_roles` for that User remained empty (`[]`) both before and after. Confirmed
again through the integration test suite (`commander.assign` tests query `userRoles` directly
before/after).

## Participant model

`incident_participants` unified across `participant_type ∈ {user, contact}` (schema also allows
`guest`, unused). A registered User and a Contact can both be added; the same identity cannot be
added twice while active (`409 duplicate_participant`, backed by the two partial unique indexes).
Removal is a soft status change (`status → 'removed'`), consistent with this codebase's existing
never-hard-delete convention (Contacts/Groups/Templates) — the roster keeps full historical
accountability for who was on an Incident and when. A participant's `sourceStatus` (the
underlying User/Contact's own current status) is always surfaced, even after that User/Contact is
later disabled — live/integration-verified that historical participation stays visible with
`sourceStatus: "inactive"` rather than being hidden.

## User/Contact separation verification

Grepped and integration-tested: adding a Contact as a participant never creates a `users` row
(row count asserted unchanged); a Contact never gains login credentials, a session, or an RBAC
role. A User remains addable to multiple different Incidents concurrently.

## Guest compatibility / exclusion

`participant_type` and related columns remain wide enough for a future `'guest'` value and a
future guest-scoped access token, but **no Guest creation, invitation, secure link, or OTP
verification exists in this module** — confirmed via grep (no `guest`/`otp`/`invite` code paths
in `backend/src/modules/incidents/`).

## Timeline architecture

`incident_timeline_events`: append-only, incident-scoped, globally-ordered via a `serial seq`
column (tiebreaker for same-`occurred_at` events), `metadata` jsonb with **no PII** (verified via
an integration test asserting a Contact's `firstName` never appears in serialized timeline JSON).
Every mutating incident operation appends exactly one (or two, for commander-assign-at-creation)
timeline event inside the same `db.transaction()` as the business-state write.

## Timeline vs audit

Two separate tables, written atomically together via a shared transaction on every mutation:
`incident_timeline_events` (operational, incident-scoped, PII-free, meant for the future Incident
Command Center UI) vs `audit_logs` (global, compliance/security-oriented, existing since Module
01, now also tagged with `incident_id` — that column existed but was unused until this module).
Both are populated from the same 10 new event-type constants; live-verified all 9 audit rows for
a single Incident's full lifecycle walk are present with correct actor attribution.

## Permission mapping

New codes: `incidents.read`, `incidents.create`, `incidents.update`,
`incidents.lifecycle.manage`, `incidents.commander.assign`, `incidents.participants.manage`,
`incidents.timeline.read`.

| Role | Grants |
|---|---|
| ADMIN | all |
| INCIDENT_COMMANDER | `users.read` (newly justified — see below), `contacts.read`, `groups.read`, `templates.read`, all `incidents.*` |
| COMMUNICATION_MANAGER | (existing 13) + `incidents.read`, `incidents.create`, `incidents.timeline.read` |
| RESPONDER | `incidents.read`, `incidents.timeline.read` |
| AUDITOR | (existing 6) + `incidents.read`, `incidents.timeline.read` |

`INCIDENT_COMMANDER` was granted `users.read` in this module — withheld in Module 03 because
nothing in the role's job justified it then. Module 08 gives it a concrete need: searching active
BEACON Users to assign/change a Commander reuses the existing `users.read`-gated `GET /users`
endpoint rather than duplicating it behind a second permission (rejected as a hidden-route
privacy-bypass risk, the same reasoning Module 06 applied to Contact lookups).

Seed re-verified idempotent: 28 permissions, 65 role-permission mappings, unchanged across
repeated `db:seed` runs.

## Concurrency protections

Two complementary techniques: (1) lifecycle transitions are a single conditional `UPDATE ... WHERE
status = <expected>`, atomic by construction; (2) operations that check-then-act across statements
(commander assign, participant add, metadata update) row-lock the Incident via `SELECT ... FOR
UPDATE` inside a `db.transaction()` for the duration of the check. A new shared `DbOrTx` type
(`database/src/client.ts`) lets every query/audit helper function work identically standalone or
inside a transaction — the first use of `db.transaction()` anywhere in this codebase.

## Privacy / security review

- No role-name checks anywhere in `backend/src/modules/incidents/` — permission-based only.
- No `console.log`, no provider/Twilio/SendGrid references, no chat/WebRTC/Agora/LiveKit code, no
  guest/OTP references, no alert-send references (all grep-confirmed empty).
- Participant list dual-gated on `incidents.read` + `contacts.read` (Contact PII embedded).
- Every mutating route (10 of 14) calls `requireCsrf`; verified exact 1:1 count match.
- `additionalProperties: false` on every body schema; mass-assignment (forged `status`,
  `incidentCommanderId`, `id`) verified ignored via integration test.
- 204 responses call `.send()` explicitly (the Module 06-discovered browser-rejection bug).
- CORS `methods` list includes `PATCH`/`DELETE` explicitly (the Module 06-discovered bug);
  re-verified live in the browser for this module's POST/PATCH/DELETE calls.

## Live API workflow

Full curl-driven workflow against the real running backend: ADMIN login → create Incident
(server-generated `INC-2026-NNNNNN` number, verified format and uniqueness) → assign User A as
Commander (verified `user_roles` unchanged) → add User A + Contact A as participants → duplicate
Contact add rejected `409` → severity change → activate → timeline verified → remove Contact A
(Contact still exists afterward) → resolve → close → metadata update / participant add / commander
change / further lifecycle all rejected `409` while CLOSED → full 9-event timeline and 9-row
audit trail verified → RBAC matrix confirmed for COMMUNICATION_MANAGER (create ok, lifecycle
forbidden), AUDITOR (read-only), RESPONDER (read-only), INCIDENT_COMMANDER (full management),
and unauthenticated (401).

One curl-only false alarm during this pass: manually adding a `Content-Type: application/json`
header to bodyless `POST`/`DELETE` requests triggered Fastify's `FST_ERR_CTP_EMPTY_JSON_BODY`,
which the app's generic error handler currently surfaces as a `500` instead of respecting the
error's own `400` `statusCode`. Confirmed this **cannot** happen from the real frontend — its
`apiFetch` wrapper only sets `Content-Type` when a body is actually present — so it did not
block validation, but it's a pre-existing, module-independent gap in `app.ts`'s error handler
(present since Module 01) worth a future look. See Limitations.

## Known limitations / follow-up

- `incident_number_seq` is a single global sequence, not reset per calendar year — the year in
  `INC-{year}-NNNNNN` reflects creation time, but the numeric suffix keeps counting across year
  boundaries rather than restarting at `000001`. A deliberate tradeoff to avoid year-rollover
  counter complexity; acceptable since the full string (including year) stays unique regardless.
- `app.ts`'s generic error handler does not special-case a `FastifyError` with its own
  `statusCode` (e.g. a malformed-body parse error) — it falls through to a generic `500`. Not
  introduced by this module and not reachable from the real frontend (confirmed above), but worth
  fixing generically in a future pass.
- No Alert Engine, provider integration, realtime Chat, War Room, or Guest invitation/OTP — all
  explicitly out of scope per this module's spec, deferred to Modules 09+.
